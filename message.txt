# ФИНАЛЬНЫЙ PROMPT — UZBITE RESTAURANT DESKTOP

## Разработка полноценного Windows-приложения `.exe` для ресторанов UzBite с двумя режимами доставки, Socket.IO, Yandex Maps и Excel/CSV

Ты — Senior Full-Stack Developer, Desktop Application Developer, React Developer, Backend Engineer, Software Architect, Database Engineer и UI/UX Designer.

Твоя задача — **разработать полноценный аккаунт Ресторана UzBite в виде отдельной Windows-программы `.exe`**, подключённой к общей системе UzBite.

Это следующий этап существующего проекта.

**Не создавать UzBite заново, не переписывать пользовательскую часть и не разрабатывать ресторанный кабинет как обычный сайт вместо Windows-приложения.**

Нужно получить настоящее настольное приложение, которое можно установить или запустить на Windows, авторизоваться в ресторанном аккаунте, управлять рестораном, публиковать блюда и видео, принимать заказы, подтверждать оплату и организовывать доставку.

Все важные действия должны работать через настоящий Backend, Socket.IO и PostgreSQL.

# 1. Главная архитектура платформы UzBite

UzBite состоит из трёх клиентских приложений и одного общего Backend.

## 1.1. Приложение для пользователей

**Платформа: мобильное приложение.**

Назначение:

- Просмотр видеоленты.
- Поиск ресторанов.
- Просмотр профилей.
- Лайки.
- Комментарии.
- Подписки.
- Корзина.
- Оформление заказов.
- Выбор адреса.
- Оплата.
- Отслеживание статусов доставки.
- Оставление отзывов.

## 1.2. Приложение для ресторанов

**Платформа: Windows Desktop Application.**

**Формат: `.exe`.**

Назначение:

- Регистрация и авторизация ресторана.
- Dashboard.
- Управление заказами.
- Управление оплатой.
- Управление меню.
- Управление категориями.
- Публикация видео.
- Управление профилем.
- Настройка местоположения.
- Организация доставки.
- Работа с собственными курьерами.
- Поиск заказных курьеров.
- Excel/CSV.
- Статистика.
- Уведомления.

## 1.3. Приложение для курьеров

**Платформа: мобильное приложение.**

Курьерский аккаунт будет разрабатываться отдельно, но его взаимодействие с рестораном необходимо предусмотреть уже сейчас.

Курьеры смогут работать в двух режимах:

1. **Собственный курьер конкретного ресторана.**
2. **Свободный курьер, принимающий заказы от ресторанов по принципу такси.**

## 1.4. Общая серверная архитектура

Все три приложения используют:

- Один Backend.
- Одну PostgreSQL.
- Одну систему авторизации и ролей.
- Одну систему заказов.
- Один Socket.IO сервер.
- Одну систему уведомлений.
- Единые статусы заказов.
- Единые данные ресторанов, пользователей и курьеров.

**Не создавать три отдельные базы данных или три независимых Backend.**

```text
                  │
                  │ REST API + Socket.IO
                  │
                  ▼
┌────────────────────────────────────┐
│ ОБЩИЙ UZBITE BACKEND               │
│                                    │

│ MOBILE           │ │ MOBILE           │
│ UzBite User      │ │ UzBite Courier   │
│                  │ │                  │
│ Покупатель       │ │ Курьер           │
└──────────────────┘ └──────────────────┘
```

## Главное требование

Когда пользователь оформляет заказ на телефоне:

1. Заказ отправляется на общий Backend.
2. Backend сохраняет заказ в PostgreSQL.
3. Socket.IO уведомляет нужный ресторан.
4. Заказ появляется в Windows-приложении ресторана.
5. Ресторан принимает заказ.
6. Пользователь получает обновление.
7. Ресторан выбирает способ доставки.
8. При необходимости заказ передаётся в мобильный курьерский аккаунт.
9. Курьер подтверждает получение задания.
10. Все участники получают разрешённые обновления статуса.

**Никаких независимых локальных заказов, существующих только внутри `.exe`.**

# 3. Важное ограничение текущего этапа

Этот промпт предназначен для реализации:

**Windows-приложения Ресторана + необходимых серверных функций взаимодействия с пользователями и курьерами.**

Мобильные приложения Пользователя и Курьера не нужно переписывать или создавать заново в рамках этого этапа.

Однако необходимо:

- Согласовать API.
- Подготовить серверную бизнес-логику доставки.
- Реализовать ресторанную сторону назначения курьера.
- Реализовать Socket.IO события.
- Подготовить контракт взаимодействия с курьерским приложением.
- Интегрироваться с уже существующими мобильными клиентами, если они разработаны.

**Если курьерского мобильного приложения пока нет, не считать полный сценарий курьерской доставки реализованным и протестированным.**

В этом случае подготовить рабочую серверную часть, ресторанный интерфейс и документированные API/события для будущего курьерского приложения.

Не создавать фиктивное принятие заказа курьером по таймеру.

# 8. Локальное тестирование через Wi-Fi без удалённого сервера

**До появления реального удалённого сервера UzBite должен работать внутри одной локальной сети Wi-Fi.**

Один компьютер запускает Backend.

На этом же компьютере может работать `UzBite Restaurant.exe`.

Телефоны подключаются к Backend через IP компьютера.

## Пример

Компьютер имеет адрес:

`192.168.1.100`

Backend:

`http://192.168.1.100:8081`

Socket.IO:

`http://192.168.1.100:8081`

Ресторанное приложение:

`UzBite Restaurant.exe`

Пользовательское мобильное приложение подключается к:

`192.168.1.100:8081`

Курьерское мобильное приложение подключается к тому же адресу.

## Очень важное правило

**Не использовать `localhost` в конфигурации API мобильных приложений при подключении к компьютеру.**

На телефоне `localhost` обозначает сам телефон.

Для подключения к компьютеру использовать его LAN IP.

Ресторанное приложение может обращаться к локальному Backend через `localhost`, если Backend работает на том же компьютере, но предпочтительно иметь общую конфигурируемую настройку адреса сервера.

# 9. Настройка Backend для LAN

Backend должен использовать порт:

**8081**.

В режиме локального тестирования сервер должен принимать подключения через сетевой интерфейс компьютера.

Предусмотреть:

- `HOST=0.0.0.0` для режима LAN.
- `PORT=8081`.
- Корректные CORS-правила.
- Подключение Socket.IO.
- Поддержку WebSocket.
- Обработку переподключений.
- Проверку JWT.
- Логирование ошибок подключения.

## Конфигурация клиентов

Не прописывать IP компьютера жёстко во всех файлах.

Использовать переменную или настройку:

```env
UZBITE_API_BASE_URL=http://192.168.1.100:8081
```

Для мобильных приложений название переменной может соответствовать используемому мобильному фреймворку.

Предусмотреть возможность изменения адреса сервера без изменения бизнес-логики.

Для Windows-приложения создать экран настройки подключения или безопасный конфигурационный механизм.

## Проверки

Обязательно протестировать:

1. Компьютер и телефон находятся в одной сети.
2. Backend доступен с телефона.
3. Авторизация работает с телефона.
4. Создание заказа работает.
5. Ресторан получает заказ.
6. Socket.IO обновляет состояние.
7. При потере Wi-Fi клиент показывает ошибку соединения.
8. После восстановления сети данные синхронизируются.
9. Повторная отправка запроса не создаёт дублирующий заказ.

## Ограничения

Локальный Backend должен быть доступен только доверенной сети.

Не открывать порт 8081 в публичный интернет ради тестирования.

Не отключать проверку JWT.

Учитывать, что HTTP в локальной сети не шифрует трафик. Для производственной среды использовать HTTPS/WSS, а для чувствительного LAN-тестирования по возможности также предусмотреть защищённое соединение.

Мобильные ОС могут ограничивать незашифрованный HTTP. Настроить необходимые разрешения только для режима разработки, не ослабляя production-безопасность.

# 17. Статусы заказов

3. **Готовится**.
4. **Доставляется**.
5. **Доставлено**.

Дополнительный статус:

**Отменено**.

Не создавать второй несовместимый набор основных статусов.

- После подтверждённого завершения доставки статус становится «Доставлено».

Не менять статусы автоматически по времени.

Не разрешать произвольные переходы.

Все изменения сохранять в PostgreSQL и отправлять через Socket.IO.

# 18. ДВА РЕЖИМА ДОСТАВКИ — ГЛАВНОЕ НОВОВВЕДЕНИЕ

**Ресторан должен иметь возможность использовать два способа доставки:**

## Режим A — Собственные курьеры ресторана

Ресторан самостоятельно выбирает одного из курьеров, прикреплённых к его ресторану.

## Режим B — Заказные курьеры UzBite

Ресторан создаёт запрос на доставку для свободных курьеров UzBite.

Принцип работы напоминает заказ такси:

- Ресторан размещает запрос.
- Подходящие свободные курьеры получают предложение.
- Курьеры могут принять или отклонить.
- Ресторан ожидает подтверждения.
- Первый успешно принявший доступное предложение получает доставку.
- После назначения курьер выполняет заказ.

**Оба режима должны использовать одно мобильное приложение UzBite Courier и один Backend.**

Не создавать два отдельных курьерских приложения.

При смене режима необходимо соблюдать текущее состояние доставки, чтобы не возникало двойного назначения.

# 21. Назначение заказа своему курьеру

При обработке заказа ресторан выбирает:

**«Доставка своим курьером»**.

Открывается список прикреплённых курьеров.

Ресторан выбирает подходящего.

Нажимает:

**«Отправить заказ курьеру»**.

## Что происходит

1. Backend проверяет заказ.
2. Проверяет принадлежность заказа ресторану.
3. Проверяет связь курьера с рестораном.
4. Проверяет, что курьер может принять назначение.
5. Создаёт предложение доставки.
6. Отправляет Socket.IO событие выбранному курьеру.
7. Курьер видит предложение в своём мобильном аккаунте.
8. Курьер может принять или отклонить.
9. Ресторан видит результат.

## Если курьер принял

- Назначение фиксируется в PostgreSQL.
- Курьер становится исполнителем доставки.
- Ресторан видит его данные и состояние доставки.
- Курьер получает адрес ресторана и адрес покупателя в объёме, необходимом для выполнения заказа.

## Если курьер отказался

- Назначение не считается принятым.
- Ресторан получает уведомление.
- Ресторан может выбрать другого своего курьера.
- Либо переключиться на заказную доставку.

## Если курьер не отвечает

Предусмотреть срок действия предложения.

После истечения срока:

- Предложение становится недействительным.
- Ресторан получает уведомление.
- Можно отправить новое предложение.

Не считать молчание согласием.

# 22. Заказные курьеры UzBite — как заказ такси

В заказе ресторан выбирает:

**«Найти курьера UzBite»**.

Показывать окно подтверждения запроса.

## Информация о доставке

- Ресторан.
- Точка получения.
- Адрес доставки.
- Дополнительные инструкции.
- Данные о заказе, необходимые курьеру.
- Условия вознаграждения курьера.
- Время создания запроса.

Если расчёт расстояния, стоимости или времени требует отдельного сервиса маршрутизации, не показывать выдуманные значения.

## Отправка запроса

Ресторан нажимает:

**«Искать курьера»**.

Backend:

1. Создаёт заявку на поиск курьера.
2. Проверяет допустимость заказа.
3. Определяет подходящих доступных курьеров.
4. Отправляет предложения в курьерские аккаунты через Socket.IO.
5. Сохраняет активную поисковую сессию.
6. Ожидает принятия курьером.

## Интерфейс ресторана во время поиска

Показывать:

**«Ищем курьера…»**

Дополнительно:

- Индикатор поиска.
- Время с начала поиска.
- Текущий статус заявки.
- Кнопка отмены поиска.
- Сообщение, если доступных курьеров нет.

Не показывать выдуманного курьера.

Не назначать исполнителя автоматически без его согласия.

# 23. Принятие заказной доставки курьером

Когда свободный курьер получает предложение:

- Он видит информацию о доставке.
- Может нажать «Принять».
- Может нажать «Отклонить».

При принятии:

1. Мобильный клиент отправляет запрос на Backend.
2. Backend проверяет доступность заявки.
3. Проверяет права курьера.
4. Проверяет его текущую занятость.
5. Атомарно закрепляет доставку за курьером.
6. Сохраняет назначение в PostgreSQL.
7. Уведомляет ресторан.
8. Уведомляет курьера об успешном назначении.

## Главное правило

**Одну доставку может успешно принять только один курьер.**

Если два курьера нажали «Принять» одновременно, победить должен только один.

Второй получает понятное сообщение:

«Этот заказ уже принят другим курьером».

Использовать серверные транзакции, условные обновления и необходимые ограничения PostgreSQL.

Не решать проблему конкурентного принятия только на Frontend.

# 24. Что происходит после нахождения заказного курьера

Когда заявка успешно принята:

В Windows-приложении ресторана показывать:

- «Курьер найден».
- Имя или разрешённые данные курьера.
- Статус назначения.
- Информацию о времени принятия.

Уведомление должно поступить через Socket.IO.

Ресторан должен видеть, что больше не требуется искать другого курьера.

## Передача заказа

Когда еда готова:

- Ресторан отмечает готовность заказа.
- Курьер получает соответствующее событие.
- Курьер прибывает за заказом.
- Ресторан передаёт заказ.
- Факт передачи подтверждается предусмотренным действием.
- Заказ получает состояние доставки «Передан курьеру».

После фактического начала движения к покупателю основной статус становится:

**«Доставляется»**.

Не переводить заказ в доставку просто потому, что курьер нажал «Принять».

# 25. Общая модель доставки

Основной статус заказа и состояние доставки должны быть **разделены**.

## Основной статус заказа

```text
WAITING_ACCEPTANCE
ACCEPTED
PREPARING
DELIVERING
DELIVERED
CANCELLED
```

## Тип доставки

```text
OWN_COURIER
ON_DEMAND_COURIER
```

## Пример состояний назначения

```text
NOT_REQUESTED
SEARCHING
OFFERED
ASSIGNED
COURIER_ACCEPTED
READY_FOR_PICKUP
PICKED_UP
ON_THE_WAY
DELIVERED
FAILED
CANCELLED
```

Точные названия согласовать с существующим Prisma Schema.

Не дублировать одно и то же состояние в противоречащих полях.

## Важная логика

Основной заказ может иметь статус:

**«Готовится»**,

а его курьерское назначение:

**«Курьер найден»**.

Это нормальная ситуация.

Не смешивать приготовление еды с назначением курьера.

# 26. Отмена и повторный поиск курьера

Предусмотреть ситуации:

- Нет свободных курьеров.
- Курьер отказался.
- Курьер не ответил.
- Поиск истёк.
- Курьер отменил принятое назначение.
- Курьер потерял соединение.
- Ресторан отменил поиск.
- Заказ отменён покупателем или рестораном по разрешённым правилам.

## Повторный поиск

Если курьер не найден:

- Показывать понятное сообщение.
- Предоставить кнопку «Повторить поиск».
- Разрешить смену режима доставки, если она допустима.
- Не создавать дублирующие активные назначения.

## Отмена назначенной доставки

Если курьер уже принял заказ, отмена назначения должна проходить через отдельную серверную операцию с проверкой допустимости.

Нельзя просто удалить курьера из поля заказа на Frontend.

Если заказ уже передан курьеру, нельзя незаметно передать его другому.

Нужен контролируемый сценарий с историей действий.

---

# 27. Стоимость доставки и оплата курьеру

Заложить в архитектуру различие между:

- Стоимостью блюд.
- Стоимостью доставки для покупателя.
- Вознаграждением курьера.
- Расходами ресторана на доставку.

**Не предполагать, что эти суммы обязательно равны.**

## Собственные курьеры

Ресторан может использовать собственные правила оплаты труда и доставки.

Не создавать полноценную зарплатную систему без отдельного требования.

## Заказные курьеры

Возможность установить или рассчитать вознаграждение за доставку.

При этом:

- Не показывать выдуманную динамическую цену.
- Не создавать автоматические списания без платёжной интеграции.
- Явно отделять фактический платёж от расчётной суммы.
- Все согласованные суммы фиксировать в Backend.

Если цена доставки для покупателя меняется после оформления заказа, нельзя списывать или требовать дополнительную оплату без согласия покупателя.

Предпочтительно определять стоимость доставки и правила её оплаты до подтверждения заказа.

Если тарифы заказных курьеров пока не реализованы, использовать явно настроенную фиксированную или тестовую политику и честно обозначить ограничения.

---

# 28. Пользователь не видит движение курьера на карте

**Это обязательное требование UzBite.**

В пользовательском мобильном приложении не показывать:

- Живую GPS-позицию курьера.
- Движущийся маркер.
- Маршрут курьера в реальном времени.
- Онлайн-карту отслеживания.

Пользователь видит только:

- Ожидание принятия.
- Принят.
- Готовится.
- Доставляется.
- Доставлено.

При необходимости — отдельные понятные сообщения о задержках.

## При этом

Ресторан и курьер могут открывать адреса через Яндекс Карты.

Это не означает, что пользователю должна показываться GPS-позиция курьера.

Не собирать непрерывную геолокацию курьера, если она не нужна для выбранной бизнес-логики.

# 29. Socket.IO для двух режимов доставки

Использовать один общий Socket.IO сервер.

## Необходимые события

Пример:

```text
order:status_updated

delivery:search_started
delivery:offer_created
delivery:offer_accepted
delivery:offer_rejected
delivery:offer_expired
delivery:courier_assigned
delivery:pickup_ready
delivery:picked_up
delivery:status_updated
delivery:completed
delivery:cancelled

payment:confirmed
payment:rejected

notification:created
```

Названия можно адаптировать к уже существующему проекту.

## Комнаты

Предусмотреть защищённые комнаты:

- Пользователя.
- Ресторана.
- Курьера.
- Заказа.
- Доставки.

## Безопасность

- JWT при подключении.
- Проверка роли.
- Проверка принадлежности заказа.
- Проверка назначения курьера.
- Запрет доступа к чужим комнатам.
- Не доверять `restaurantId` и `courierId` как доказательству прав.

## Надёжность

- PostgreSQL — источник истины.
- Socket.IO — доставка событий.
- При переподключении получать состояние через API.
- Не создавать двойные назначения.
- Использовать идемпотентность для повторных запросов.
- Учитывать, что WebSocket может временно отключаться.

# 30. Управление оплатой

Сохранить два способа:

1. Наличными.
2. Картой через реквизиты ресторана.

## Оплата картой

Покупатель:

- Видит реквизиты.
- Оплачивает самостоятельно.
- Загружает скриншот.
- Оформляет заказ.

Ресторан:

- Получает чек.
- Проверяет поступление денег.
- Подтверждает или отклоняет оплату.

## Статусы

- Ожидает оплаты.
- Ожидает подтверждения.
- Оплачено.
- Оплата отклонена.

## Правила

- Чек не подтверждает оплату автоматически.
- Подтверждение доступно только владельцу соответствующего ресторана.
- При отклонении нужна причина.
- Покупатель получает обновление.
- Начало приготовления карточного заказа возможно только после необходимого подтверждения оплаты.
- Не использовать фиктивные банковские интеграции.

## Наличные

Для наличных чек не требуется.

Предусмотреть отдельное подтверждение фактического получения наличных.

Не смешивать состояние оплаты и состояние доставки.

# 31. Управление платёжными реквизитами

В настройках ресторана:

**«Способы оплаты»**.

Поля:

- Принимать наличные.
- Принимать оплату переводом.
- Имя получателя.
- Необходимые реквизиты.
- QR-код.
- Инструкция покупателю.

Показывать пользователю только специально предназначенные для оплаты данные.

Не собирать CVV, PIN и банковские пароли.

Если реквизиты не настроены, способ оплаты картой должен быть недоступен.

При изменении реквизитов новые заказы используют новые значения.

Старые заказы сохраняют историю, необходимую для проверки.

- Впоследствии подключиться к production-серверу.

## Главный сценарий №1 — собственный курьер

**Пользователь оформляет заказ на телефоне → ресторан получает заказ в Windows `.exe` → принимает → готовит → выбирает своего курьера → курьер получает предложение в мобильном приложении → принимает → получает заказ в ресторане → доставляет покупателю → статусы обновляются у всех участников.**

## Главный сценарий №2 — заказной курьер

**Пользователь оформляет заказ на телефоне → ресторан получает заказ в Windows `.exe` → принимает → выбирает «Найти курьера UzBite» → Backend отправляет предложение доступным курьерам → один курьер принимает заявку → ресторан получает подтверждение → курьер забирает заказ → доставляет покупателю → статусы обновляются у всех участников.**

## Главный сценарий №3 — локальное тестирование

**Windows-компьютер запускает Backend и UzBite Restaurant.exe → телефоны пользователя и курьера подключаются к Backend через один Wi-Fi → все действия передаются через REST API и Socket.IO → данные сохраняются в общей PostgreSQL.**

## Главное архитектурное правило

**Ресторан — Windows `.exe`.**

**Пользователь — мобильное приложение.**

**Курьер — мобильное приложение.**

**Backend — один общий сервер.**

**Database — одна общая PostgreSQL.**

**Realtime — один общий Socket.IO.**

**Доставка — два режима: свои курьеры и заказные курьеры.**

**Excel и CSV — полноценный импорт и экспорт, а не декоративные кнопки.**

**Локальный Wi-Fi — для тестирования.**

**Реальный удалённый сервер — для будущего production-запуска.**
