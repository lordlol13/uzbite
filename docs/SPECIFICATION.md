# 1. Главная концепция UzBite

**Название:** UzBite.

UzBite объединяет:

- Вертикальную видеоленту блюд в стиле Instagram Reels.
- Профили ресторанов.
- Просмотр меню и публикаций.
- Лайки, комментарии и подписки.
- Подтверждённые отзывы о заказах.
- Поиск ресторанов и блюд.
- Корзину с несколькими блюдами.
- Оформление доставки.
- Выбор адреса через встроенную карту Yandex Maps.
- Сохранение адресов доставки.
- Оплату наличными или картой.
- Отслеживание статусов заказов.
- Уведомления в реальном времени.

В будущем платформа будет иметь три типа аккаунтов:

1. Пользователь.
2. Ресторан.
3. Курьер.

Официантов и дополнительные роли не создавать без отдельного требования.

## ВАЖНО: что разрабатывается сейчас

**На текущем этапе необходимо реализовать только полноценный аккаунт Пользователя.**

Аккаунты Ресторана и Курьера разрабатывать позже, на основании отдельных промптов.

Сейчас не создавать:

- Dashboard ресторана.
- Рабочие страницы ресторана.
- Управление ресторанными публикациями со стороны ресторана.
- Интерфейс приёма заказов рестораном.
- Интерфейс подтверждения оплаты рестораном.
- Курьерский кабинет.
- Курьерские заказы и назначения.
- Курьерские маршруты и рабочие процессы.
- Фиктивные реализации этих функций.

Однако пользователь уже сейчас должен иметь возможность просматривать рестораны, публикации, блюда, добавлять товары в корзину и отправлять заказы.

Для этого необходимо создать **серверную структуру данных ресторанов, меню, публикаций и заказов**, но не реализовывать интерфейсы управления ими для аккаунтов ресторанов.

До появления ресторанных аккаунтов данные ресторанов и публикаций можно загружать через Prisma Seed и отдельные инструменты разработки.

**Нельзя выдавать существование данных ресторана за готовность ресторанного аккаунта.**

# 4. Порты, localhost и Network

## Frontend

**Обязательный адрес:**

`http://localhost:8080`

Настроить Vite:

- `host: "0.0.0.0"`
- `port: 8080`
- `strictPort: true`

Приложение также должно открываться через локальную сеть:

`http://IP-КОМПЬЮТЕРА:8080`

Например:

`http://192.168.1.100:8080`

Не ограничивать доступ только localhost.

## Backend

**Порт Backend: 8081.**

Настроить Vite Proxy:

- `/api` → Backend 8081.
- `/socket.io` → Backend 8081.
- WebSocket Proxy для Socket.IO.

Frontend должен обращаться к Backend через относительные адреса, например:

`/api/restaurants`

Не использовать жёстко записанный `http://localhost:8081` в браузерных запросах.

Это важно для работы сайта через Network на телефоне.

## Проверки

Обязательно проверить:

- Frontend на порту 8080.
- Backend на порту 8081.
- API через Proxy.
- Socket.IO через Proxy.
- Открытие сайта в локальной сети.
- Работу приложения после обновления страницы.

Если порт 8080 занят, не переключаться автоматически на другой.

# 5. Один общий node_modules

Организовать проект как **npm workspaces monorepo**.

Пример структуры:

```text
UzBite/
├── package.json
├── package-lock.json
├── .npmrc
├── .gitignore
├── .env.example
├── node_modules/
├── apps/
│   ├── frontend/
│   │   ├── package.json
│   │   ├── index.html
│   │   ├── vite.config.ts
│   │   ├── .env.example
│   │   └── src/
│   └── backend/
│       ├── package.json
│       └── src/
├── packages/
│   └── shared/
├── prisma/
│   ├── schema.prisma
│   ├── migrations/
│   └── seed.ts
├── docs/
│   ├── PROJECT_STATUS.md
│   └── CHANGELOG.md
└── README.md
```

Требования:

1. Один главный `package.json` в корне.
2. Один общий `package-lock.json`.
3. Основная директория `node_modules` находится в корне.
4. Зависимости устанавливаются из корня проекта.
5. Не запускать отдельные `npm install` внутри Frontend и Backend.
6. Согласовать версии зависимостей для корректного hoisting.
7. Не создавать самостоятельные независимые установки зависимостей.
8. Использовать npm workspaces для запуска Frontend и Backend.

Если npm из-за несовместимости пакетов создаёт вложенные зависимости, устранить конфликт версий, где это возможно, и честно сообщить о техническом ограничении.

# 12. Главная — видеолента UzBite

Создать вертикальную видеоленту по принципу Instagram Reels.

Каждая публикация занимает основную часть экрана.

Функциональность:

- Вертикальная прокрутка.
- Автоматическое воспроизведение текущего видео.
- Остановка предыдущего видео.
- Лайки.
- Комментарии.
- Поделиться.
- Переход в профиль ресторана.
- Добавление блюда в корзину.
- Просмотр информации о блюде.

## Верхняя панель

Слева — логотип UzBite.

Справа — переключатель:

- **Лента**.
- **Подписки**.

«Лента» показывает доступные публикации всех ресторанов.

«Подписки» показывает публикации только ресторанов, на которые подписан пользователь.

Если подписок нет, показывать понятное пустое состояние.

## Правая панель видео

### Иконка ресторана

Открывает профиль соответствующего ресторана.

### Иконка лайка

Первое нажатие ставит лайк.

Повторное нажатие убирает лайк.

Лайк сохраняется в PostgreSQL и отображается во вкладке «Понравившиеся».

### Иконка комментариев

Открывает Bottom Sheet примерно на 80% высоты мобильного экрана.

Внутри:

- Комментарии.
- Аватары.
- Имена.
- Время публикации.
- Ответы.
- Поле ввода.
- Отправка комментария.
- Состояния загрузки и ошибок.

### Иконка поделиться

Использовать Web Share API, если поддерживается браузером.

Если не поддерживается — предоставить копирование ссылки.

## Информация в нижней части

Показывать:

- Название ресторана.
- Рейтинг.
- Название блюда.
- Краткое описание.
- Цену.

Добавить заметную оранжевую кнопку **«Заказать»**.

### Важная логика кнопки

Кнопка «Заказать» **не создаёт заказ мгновенно**.

Она добавляет блюдо в корзину и открывает вкладку «Заказы» с корзиной.

# 18. Yandex Maps — окончательная логика интеграции

**Использовать Yandex Maps JavaScript API 3.0.**

Нужна полноценная интерактивная карта внутри UzBite для выбора адреса доставки.

## Предоставленный API-ключ

Для локальной разработки уже предоставлен ключ:

```env
VITE_YANDEX_MAPS_API_KEY=<local-key-stored-only-in-ignored-env>
```

Ключ создан для продукта **JavaScript API**.

В кабинете Яндекса на момент предоставления ключа отображается статус **«Активен»**.

Настроено ограничение HTTP Referer:

`localhost`

Не просить пользователя повторно предоставить этот ключ.

Использовать его для локальной интеграции.

Однако успешную фактическую загрузку карты нужно проверить отдельно.

## Как хранить ключ

- В `apps/frontend/.env` для локальной разработки.
- Читать через `import.meta.env.VITE_YANDEX_MAPS_API_KEY`.
- Не прописывать значение непосредственно в React-компонентах.
- Не добавлять реальное значение в `.env.example`.
- Не включать `.env` в Git.
- Не выводить ключ в отчётах или логах.
- Для production настроить разрешённый домен.

Помнить, что JavaScript API работает в браузере, поэтому клиентский API-ключ технически доступен пользователям сайта. Основная защита — ограничения в кабинете Яндекса.

## Подключение

Использовать официальный скрипт API 3.0:

`https://api-maps.yandex.ru/v3/?apikey=API_KEY&lang=ru_RU`

Реализовать корректную асинхронную загрузку.

Дождаться `ymaps3.ready` перед инициализацией карты.

Не подключать API 2.1 вместо 3.0.

Не смешивать объекты и методы версий 2.1 и 3.0.

Создать отдельный переиспользуемый компонент, например:

`YandexLocationPicker`.

# 19. Выбор адреса доставки через встроенную карту

## Первый заказ

Когда пользователь впервые оформляет заказ:

1. Нажимает «Выбрать адрес доставки».
2. Внутри UzBite открывается интерактивная карта Яндекса.
3. Пользователь выбирает точку на карте.
4. На выбранной точке появляется маркер.
5. Маркер можно переместить или выбрать другую точку.
6. Пользователь подтверждает выбор.
7. Точка возвращается в форму оформления заказа.
8. Пользователь при необходимости уточняет адрес.
9. Адрес сохраняется в его аккаунте.

**Не заставлять пользователя переходить в Яндекс Карты, копировать ссылку и возвращаться в UzBite.**

Весь выбор должен происходить внутри сайта.

## Выбор точки

Реализовать:

- Выбор нажатием на карту.
- Визуальный маркер выбранной точки.
- Изменение точки.
- Подтверждение.
- Отмену без сохранения.
- Корректную работу на сенсорных экранах.

При наличии разрешения пользователя можно добавить кнопку определения текущего местоположения.

Если геолокация недоступна, карта всё равно должна позволять **выбрать точку вручную**.

## Автоматическое определение местоположения

Учитывать:

- Запрос разрешения у пользователя.
- Возможность отказа.
- Ошибки определения.
- Недоступность GPS.
- Требование HTTPS для браузерной геолокации на обычных сетевых адресах.

Для `localhost` браузерная геолокация обычно доступна как для доверенного локального адреса.

При открытии сайта на телефоне через `http://192.168.x.x:8080` автоматическая геолокация может быть недоступна из-за отсутствия HTTPS.

В этом случае нельзя ломать оформление заказа: ручной выбор точки должен работать независимо.

## Данные адреса

Предусмотреть:

- Широту.
- Долготу.
- Текстовый адрес.
- Название адреса, например «Дом» или «Работа».
- Подъезд.
- Этаж.
- Квартиру.
- Комментарий курьеру.
- Признак основного адреса.

Учитывать, что Yandex Maps API 3.0 использует порядок координат `[longitude, latitude]`.

Во внутренней модели использовать понятные поля `latitude` и `longitude`, чтобы избежать перепутывания.

## Определение адреса по точке

Если для преобразования координат в текстовый адрес необходим Геокодер:

- Проверить доступность нужной функции по тарифу и ключу.
- Не предполагать, что отдельный Геокодер автоматически включён.
- При отсутствии доступного геокодирования пользователь должен иметь возможность самостоятельно ввести текстовый адрес.
- Никогда не показывать выдуманный адрес.

Соблюдать лицензионные условия сохранения результатов Yandex Maps API и Геокодера. Если выбранный тариф не разрешает долговременное хранение определённых данных API, необходимо подобрать разрешённый способ реализации или подходящую лицензию и явно сообщить об ограничении.

# 25. Ручное подтверждение оплаты — будущий процесс ресторана

В архитектуре предусмотреть двухэтапное подтверждение карточной оплаты.

Процесс:

1. Пользователь выбирает оплату картой.
2. Видит реквизиты ресторана.
3. Выполняет оплату через банковское приложение.
4. Прикладывает чек.
5. Создаёт заказ.
6. Backend сохраняет сведения о платеже.
7. Заказ получает статус оплаты «Ожидает подтверждения».
8. В будущем ресторан проверяет поступление средств.
9. Ресторан подтверждает или отклоняет оплату.

## Статусы оплаты

- Ожидает оплаты.
- Ожидает подтверждения.
- Оплачено.
- Оплата отклонена.

## Правила

- Загруженный чек **не является доказательством успешного поступления средств**.
- Нельзя автоматически помечать платёж как оплаченный только из-за наличия скриншота.
- Только уполномоченная сторона может подтвердить платёж.
- При отклонении оплаты сохранять причину.
- При карточной оплате не начинать приготовление без необходимого подтверждения.
- При наличной оплате действуют другие правила.

**Сейчас реализовать пользовательскую часть подачи чека и отображения статуса.**

Интерфейс подтверждения оплаты рестораном оставить до отдельного промпта.

18. Вернуть пользователю подтверждение.
19. Очистить корзину только после успешного создания.

## Снимок данных заказа

Даже если ресторан позже изменит:

- Название блюда.
- Цену блюда.
- Адрес ресторана.
- Меню.

Уже созданный заказ должен сохранять исторически правильную информацию.

Не рассчитывать старые заказы по изменённым текущим ценам.

## Отправка адреса ресторану

В заказе должны присутствовать:

- Текстовый адрес.
- Координаты.
- Подъезд.
- Этаж.
- Квартира.
- Комментарий.

В будущем ресторан сможет открыть координаты в Яндекс Картах.

Для этого не требуется показывать пользователю карту курьера.

# 27. Статусы заказов

Использовать следующие статусы:

1. **Ожидание принятия**.
2. **Принят**.
3. **Готовится**.
4. **Доставляется**.
5. **Доставлено**.

Дополнительный терминальный статус:

- **Отменено**.

## Отображение

На странице заказа показывать:

- Текущий статус.
- Этапы выполнения.
- Время обновления.
- Информацию о ресторане.
- Состав заказа.
- Сумму.
- Статус оплаты.

Использовать красивые SVG-иконки и визуальный индикатор этапов.

## Важное правило

**Пользователь не видит GPS-позицию курьера.**

Не создавать:

- Живую карту движения курьера.
- Автоматически движущийся маркер.
- Фиктивную анимацию маршрута.
- Отслеживание курьера через WebSocket.

Только реальные статусы заказа.

## Ограничение текущего этапа

Поскольку ресторанный интерфейс пока не разрабатывается, заказ после оформления может находиться в статусе «Ожидание принятия» до появления реального механизма обработки рестораном.

**Не менять статусы автоматически по таймеру только для видимости работы.**

Разрешается подготовить отдельную команду или инструмент тестирования для разработчика, чтобы проверить серверную смену статуса и Socket.IO.

Но этот инструмент не должен быть доступен обычным пользователям и не должен имитировать работу ресторана в production.

Когда будет разработан ресторанный аккаунт, он подключится к уже существующей системе статусов.

# 29. Socket.IO — realtime

## Сейчас

Использовать для:

- Обновления статусов оплаты.
- Уведомлений пользователя.
- Новых комментариев и других уместных событий.

## В будущем

Через ту же инфраструктуру будут подключаться рестораны и курьеры.

## Безопасность Socket.IO

- Проверять авторизацию при подключении.
- Проверять право пользователя присоединиться к комнате заказа.
- Не позволять подписываться на чужие заказы.
- Разделять комнаты пользователей и заказов.
- Не доверять идентификаторам, переданным клиентом.
- Не отправлять конфиденциальные данные посторонним пользователям.

## Надёжность

- Источник истины — PostgreSQL.
- Socket.IO только доставляет события.
- При повторном подключении получать актуальное состояние через API.
- Обрабатывать разрывы соединения.
- Автоматически переподключаться.
- Избегать дублирующих событий.
- Не терять историю заказов при обновлении страницы.

Не создавать сейчас ресторанные и курьерские Socket.IO интерфейсы.

# 38. Лицензирование Yandex Maps и сетевые ограничения

При реализации Yandex Maps обязательно учитывать следующие правила.

## HTTP Referer

Для `http://localhost:8080` уже настроено ограничение:

`localhost`

Для открытия сайта через локальный IP компьютера может потребоваться дополнительная настройка разрешённого источника в кабинете Яндекса.

Не считать, что `localhost` автоматически разрешает все IP-адреса локальной сети.

В документации указать точные действия для проверки и настройки Network.

## Яндекс Карты и хранение данных

Не предполагать, что наличие активного API-ключа автоматически разрешает любые коммерческие сценарии и долговременное хранение всех данных API.

Перед production-запуском проверить:

- Условия тарифа.
- Условия коммерческого использования.
- Возможность сохранения координат и адресов, полученных через API.
