# Фактическое состояние UzBite

8 ноября 2026 · версия 0.1.0 · пользовательский веб-модуль.

Создана запускаемая локальная пользовательская версия с настоящим Express API и PostgreSQL. Это не завершённая платформа доставки: рабочие кабинеты ресторана и курьера отложены, облачные интеграции требуют настройки. Источник требований сохранён в SPECIFICATION.md с удалённым значением ключа карты.

### Данные и бизнес-правила

Prisma-модели: User, UserSettings, Session, UserAddress, Restaurant, RestaurantCategory, Dish, Post, PostMedia, Like, Comment, Follow, Review, Order, OrderItem, Payment, Upload, Notification. Используется PostgreSQL 18.6 на loopback:5432. Денежные значения хранятся Decimal(14,2); итог рассчитывается Decimal на сервере. В JSON сумма передаётся числом для отображения.

Миграция 202611080001_init применена. Она содержит частичный уникальный индекс Order_one_active_per_user, индекс одного основного адреса и ограничения рейтинга, количества, денежных значений и координат. Serializable-транзакция и индекс защищают от двух активных заказов. Исторические названия, цены, ресторан и адрес копируются в заказ.

Seed создаёт 6 вымышленных демонстрационных ресторанов, 18 блюд и 6 публикаций: 2 настоящих лицензированных видео и 4 фотографии. Готовые отзывы, фиктивные рейтинги, пользователи и платёжные реквизиты не создаются. Источники перечислены в MEDIA_SOURCES.md.

Рабочие семейства API: /api/auth, /api/profile, /api/restaurants, /api/categories, /api/feed, /api/posts, /api/addresses, /api/orders, /api/notifications, /api/uploads. Контракты приведены в API.md. Публичных API изменения статуса, подтверждения платежа и регистрации иных ролей нет.

## 3. Частично выполнено

- S3/CDN: реализованы адаптер, сигнатуры/лимиты файлов и приватные ссылки. Рабочие bucket, доступы, CDN и отдельный S3_PRIVATE_BUCKET не настроены. Успешная облачная загрузка не заявляется.
- Карточная оплата: UI подачи чека и серверные проверки реализованы. У демонстрационных ресторанов нет настоящих реквизитов/QR, поэтому CARD недоступен. Подключённый provider/receipt workflow ещё не проверен с реальными доступами. Чек не переводит платёж в PAID.
- Redis: клиент, распределённый rate limiter и канал developer-событий реализованы; Docker Compose содержит Redis. Сам Redis в текущем окружении не запущен. В development используется явно обозначенный лимитер процесса; production работает fail-closed при отсутствии Redis.
- Карта: localhost проверен. Перетаскивание маркера и полноэкранный мобильный выбор проверены после дополнительного аудита. Работу ключа с LAN Referer, отказ геолокации и сетевую ошибку карты отдельно вручную не прогоняли. Ручной выбор не зависит от геолокации; ошибки и повторная попытка предусмотрены в коде.
- Видео: два HD720 ролика отдаются локально и воспроизводятся; невидимые останавливаются. Производственный transcoding, несколько bitrate/разрешений и CDN-пайплайн ещё не подключены. Стоковые фотографии зависят от внешнего CDN; есть fallback.
- Локализация: основной интерфейс и ошибки API переведены. Имена/описания/категории и публикации ресторана являются данными каталога, а не автоматически переводимыми пользовательскими материалами. Автоматический перевод контента не создавался.

## 4. Не удалось подтвердить без внешних доступов

1. Доставку реального заказа и приём рестораном: рабочих кабинетов по заданию пока нет. Заказ честно остаётся PENDING_ACCEPTANCE; таймеров фиктивных статусов нет. Закрытый order:status инструмент работает только вне production.
2. Успешную S3/CDN загрузку и карточный чек с настоящими реквизитами — нет необходимых доступов.
3. Геокодер и коммерческие права хранения результатов API — не предоставлены отдельная лицензия/сведения о тарифе. Пользователь вводит текст адреса самостоятельно; выдуманных результатов геокодирования нет. Права долговременного хранения выбранных координат нужно подтвердить по договору Яндекса перед production.
4. Доступ с физического телефона: сетевой HTTP/API/WebSocket проверены через IPv4 с текущего компьютера, но отдельный телефон не подключался. Windows Firewall и Referer ключа требуют проверки на целевом устройстве. На HTTP LAN автоматическая геолокация может требовать HTTPS.

Обнаруженные и исправленные ограничения среды: PostgreSQL запрещал прямой запуск из административного терминала Windows — используется pg_ctl со сниженным токеном без создания системного пользователя/службы. Повторная генерация Prisma при работающем API блокировала Windows DLL — build больше не перегенерирует Client; db:generate выполняется отдельно после изменения схемы при остановленном API.

## Дополнительный аудит и исправления

По запросу продолжить разработку исправлены найденные недоделки пользовательского модуля:

- Корзина сохраняется в отдельном ключе для каждого аккаунта. Смена пользователя очищает чужие клиентские данные и загружает собственную корзину; блокировка browser storage не ломает приложение. Неразмеченный старый development-ключ не присваивается другому пользователю.
- Язык/тема регистрации передаются серверу; последовательная очередь сохранения настроек предотвращает потерю быстрых переключений. Уведомления REST/Socket локализуются по актуальным настройкам на RU/UZ/EN; старые строки без metadata также читаются.
- Мобильный picker занимает 100dvh, сохраняет выбранную точку при пересоздании карты, не принимает устаревший callback геолокации. Кнопка геолокации не закрывает атрибуцию Яндекса. Из оформления можно редактировать выбранный адрес через ту же карту.
- Заказы, лайки, подписки, комментарии и уведомления поддерживают настоящую пагинацию; старые записи больше не отсекаются лимитом200. Frontend подгружает следующие страницы с сохранением уже загруженных данных при ошибке.
- URL и оба поля поиска согласованы, включая повторный запрос из шапки и Back/Forward. Цены строк и суммы корзины берутся из server quote; изменения отмечаются, неподтверждённый расчёт не позволяет отправить заказ.
- В ленте один владелец воспроизведения. Загруженные источники сохраняют позицию, следующий ролик предзагружается с учётом Data Saver/скорости сети. Обработаны блокировка autoplay, повторная попытка и ошибка общей ссылки. Добавлены информация о блюде и fallback копирования для HTTP LAN.
- Диалоги поддерживают Escape, Tab/Shift+Tab и возврат фокуса; смена ресторана требует подтверждения.
- Проверки никнейма выполняются внутри транзакции; телефон можно очистить. Все проверки пароля согласованы по72UTF-8байтам. Исправлены отзыв Socket при logout с refresh-cookie, абсолютный срок сессии, неверный ack и дубли в объединённых комнатах.
- Закрытый developer-инструмент проверяет переходы оплаты, хранит причину отказа и не разрешает готовить/завершать CARD без подтверждения. Новых публичных методов смены статуса нет.

## Уточнения пользователя: белые поверхности и простая регистрация

По уточнению от 9 ноября регистрация и вход содержат только почту и пароль. Новая регистрация требует email, нормализованный по регистру и пробелам. При создании аккаунта назначается временный никнейм; пользователь задаёт свой в настройках профиля. Первая установка доступна сразу, последующие изменения — раз в 30 дней. Никнейм не используется для входа. Существующие записи не перезаписываются; прежние аккаунты без email могут добавить почту в настройках при действующей сессии. Поле email остаётся nullable в БД для сохранения этих записей. Имя получателя доставки хранится отдельно и не перезаписывает имя профиля.

Светлые заливки карточек, панели ленты, аватара и форм заменены белыми, включая прежнюю бежевую промокарточку. Текстовая надпись UzBite возвращена, иконка рядом удалена. Тёмная тема и основные оранжевые кнопки сохранены.

Проверено после перехода на почту: build (включая TypeScript), ESLint и 17 интеграционных групп на реальном PostgreSQL, включая регистрацию с двумя полями, дубликат почты, нормализацию регистра, смену никнейма и последующий вход по прежней почте.

### Реализованные компоненты

1. **PostgreSQL и Prisma (`202611170003_restaurant_desktop_delivery_excel`)**:
